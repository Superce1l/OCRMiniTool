## 0. 结论（先看这一页）

### 0.1 一句话结论

代码底子比预期好（stdlib-only、状态机互斥正确、路径穿越与 multipart 解析实测稳健），
**真正的问题集中在四类"账没算清"的地方**：① 宣称的能力有 3 项是空的（缩放/取消/卸载）；
② 外部输入能突破本机安全边界（OCR 结果的 HTML 直通 → XSS → 同源 API）；
③ 最贵的资源（6.8 GB 模型 / 3.3 GB 组件）缺完整性链条与时长上限；
④ 工程基线缺失（行尾事故、零测试、依赖口径五处漂移、发布不可复现）。

### 0.2 必须知道的三件事

| # | 结论 | 证据强度 |
|---|---|---|
| 1 | **XSS 是真实可利用的**：自研 Markdown 对"行首为 HTML 块"的整行原样写入 `innerHTML`，`<div><img src=x onerror=…></div>` 会执行。恶意图片/PDF 被 OCR 转写 → 渲染即执行 → 同源下可改设置、删历史、外泄 `outputs/*.md`、触发 6.8 GB 下载、`/api/shutdown`；结果落盘后点历史是**存储型**复发 | **实测**（抽出原函数跑 9 条 payload，6 条原样通过）+ `app.js:265,293-295` → `:355` |

## 3. 四个领域的结论（细节见各子报告）

### 3.1 推理性能与资源 — `docs/explore/01-engine-perf.md`

| 结论 | 依据 |
|---|---|
| CPU 上**解码是内存带宽瓶颈**：每 token 需读 ~1.15 GB 权重（MoE 6/64 + lm_head + 注意力），本机实测带宽 8–12 GB/s ⇒ 理论上限 ~10 tok/s | 实测带宽 + 代码推理 |
| 更糟的是**每 token 把整份 KV 缓存 `.float()` 两遍**（`modeling_deepseekv2.py:475-476`），流量 ∝ 序列长度：20 页合并时 ~2.4 GB/token ⇒ ~5 tok/s。**合并模式的页数直接决定每 token 速度** | 代码推理（高置信） |
| 单页耗时被**视觉塔**主导：日志实测单页 108 s 只出 63 字；粗算视觉 ~1.5 TFLOP ⇒ 有效算力 ~15 GFLOPS，而同机 fp32 GEMM 实测 496 GFLOPS ⇒ **bf16-on-CPU 走仿真路径**<br>**✅ 已证实并落地（A12）**：真机交错 A/B，视觉塔改 fp32 后 prefill **47.3 s → 10.9 s（4.3×）**，单页端到端 120.3 s → 18.8 s，输出**逐字节一致**；CPU 默认已切 fp32 | 日志实测 + 真机 A/B |
| 生成无上限：`max_new_tokens` 默认 `131072 - prompt_len` 且后端不传值 ⇒ 最坏 13 万 token（CPU ~4 小时），无看门狗 | 事实 |
| 取消只在解码每 token 生效，**视觉 + prefill 完全不可中断**（单页可达 ~100 s）；README 第 27 行"取消 1～2 秒内生效"与代码不符 | 事实 |
| 后处理不是瓶颈：100 页 / 235 KB 原始输出 `convert()` 仅 **60 ms**（0.6 ms/页），**不建议优化** | 实测 |
| 不建议：`torch.compile`、强制 flash-attn/sdpa、关 DASH、int8/4bit 量化、多页并行、自实现 mmap 加载、暴露 temperature | 各有具体理由（见报告 §8） |

### 3.2 功能拓展 — `docs/explore/05-feature-expansion.md`

关键核实（决定了哪些提案值得做）：

- **坐标有，但被丢了**：模型输出 `<BLOCK>label<LEVELn>[x1,y1,x2,y2]<FORK>`，`ocr_postprocess.py:99-136` 已解析出 bbox/level/page，而 `_render_blocks:252-281` 只取文字 → 这是 E2（JSON）／E8（可搜索 PDF）／E15（裁剪）的总闸门。
- **置信度没有**：`infer` 只回字符串，`return_dict` 只有 `finish_reason/num_pages_out/expected_pages/time`，logits 算完即 argmax 丢弃 → "真·置信度"判定不可行。
- **`infer` 参数面远大于仓库所用的 6 个**：还可吃 PIL.Image、`return_dict`、`base_size/image_size/max_crops`、`max_length=131072`。
- **页眉页脚现在全被留在正文里**：`DROP_LABELS = set()` 是空集合（E11，2–4 人时就能改）。

提案共 E1–E20，性价比最高三项：**E3 截断/页数检测（3–5 人时）> E5 目录扫描（1–1.5 人日）> E11 页眉页脚去重（2–4 人时）**。
不建议：真·置信度、队列持久化、文件夹拖入（Chromium 沙箱拿不到绝对路径）、再喂模型改格式、多后端热切换。

### 5.4 明确不建议做（跨领域汇总，37 条里最容易被误提的 8 条）

| 不做 | 理由 |
|---|---|
| 引入前端框架 / marked+DOMPurify | 2.5k 行零依赖前端；白名单 40 行就够，引入依赖会打破"离线零依赖" |

| 优化 `ocr_postprocess` | 实测 0.6 ms/页，占比 <0.1% |
| 真·置信度输出 | 模型不给 logprobs，只能 hack guard 钩子，换模型即失效 |
