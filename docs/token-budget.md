## 1. 为什么需要校准

- `maxPageTokens` 的 4096 来自早期估算：「一页约 1000 字」。它没有真实分布支撑。
- 实机此前只验证过两类极端：小图 75 token、长截图 973 token（`docs/实机测试报告.md:36-37`）。
  两者都远低于 4096，但都不是"密集表格页"。
- 密集版式（表格/双栏/公式）的输出可能显著更长；一旦超过上限，引擎按页截断并标
  `truncated=true`（`ocr_engine.py:1062-1078`），用户看到"识别成功"却少了内容。
- 反过来，放大默认值会让退化输出（见 §6.2）烧更久。默认值必须同时对**完整性**和
  **最坏单页时长**负责。

## 2. 指标定义（判据依赖这些字段）

单次识别（`OcrEngine.recognize`）的返回字段（`ocr_engine.py:1062-1078`）：

| 字段 | 含义 | 本方案用途 |
|---|---|---|
| `tokens` | **输出 token 数**（多组求和；模型不返回时为 `None`） | 主指标（横轴） |
| `finishReason` | 最后一组的 `stop` / `length` / `None` | **截断判据**（`length` = 撞到上限） |
| `truncated` | 任一组 `finish_reason == "length"` | 与上一行同义，便于直接断言 |
| `elapsed` | 本次识别总秒数 | 时长代价 |
| `infer` | `_summarize_infer()` 明细：`prefillSecs` / `decodeSecs` / `tokensPerSec` / `numPagesOut` / `expectedPages` | 区分 prefill 与 decode 成本 |
| `groups` | 实际分组数（未分组=1） | 确认没有误分组 |
| `effectiveMaxNewTokens` | 本次真正传的生成上限 | 确认"限幅真的生效" |
| `pagesMismatch` | 模型出页数 ≠ 提示页数 | 页数维度的完整性 |

`tokens` 来源链：模型 `_uocr_generate` 返回 `token_ids`（`modeling_unlimitedocr.py:1202-1205`）
→ `_summarize_infer` 取 `len(token_ids)`（`ocr_engine.py:253-296`，字段 `outputTokens`）
→ `_sum_tokens(group_stats)` 求和（`ocr_engine.py:1069`）。

**注意**：`tokens` 是输出文本 token，包含版面标记（`<BLOCK>`/`<PAGE>` 等）与公式符号，
不等于字数。所以"4096 够不够"必须看 token 与 `finishReason`，不能看字数。

限幅口径：
- `max_page_tokens` 由 `_normalize_page_tokens()` 归一：`0`=不限，正数夹到 **[256, 65536]**（`ocr_engine.py:326,330-336`）。
- 实际请求上限 `= min(max_page_tokens × 组内页数, 显式 max_new_tokens, 131072)`（`_effective_max_new_tokens`，`ocr_engine.py:361-376`）。

## 4. 判据（可执行，避免拍脑袋）

对每份文档 **Dx**，用 `max_page_tokens=8192`（远高于嫌疑值）跑一次，同时
`crop_mode="auto"`、单页、单实例。记录 `tokens`、`finishReason`、`elapsed`、`infer`。

- **判据 A（真实需求）**：`finishReason == "stop"` → 该文档的真实输出长度就是 `tokens`。
- **判据 B（8k 也不够 / 异常）**：`finishReason == "length"` 或**长时间不结束** → 单独归为异常类，
  不计入 p95，也不能用于"4096 是否够"的统计（D6 即此类，见 §6.2）。
- **判据 C（4096 够不够）**：`tokens ≤ 4096` 且 4096 复跑 `finishReason == "stop"` → 够；
  `tokens > 4096` → 不够；`tokens ≤ 4096` 但复跑 `length` → 按不够处理（保守）。
- **复跑规则**：只对 `tokens > 4096` 或 3500–4096 临界的文档用 4096 复跑（省 CPU）。
  本次最大 2333 < 3500，**无需复跑**。

**结论（三条）**：

1. **上限是必需的安全阀**：不设上限时模型默认上限是 `131072 - prompt`，这种退化可以把
   单页烧几小时；8192 至少把最坏单页钉在 ~30 分钟量级（4.2 tok/s × 8192 ≈ 32 min）。
2. **上限救不了退化生成**：D6 在 8192 之前就已编造+循环，用户等很久拿到的是垃圾。
   token 上限不是质量/时长的充分保障——`finish_reason` 之外还需要 **wall-clock 看门狗**，
   或按 h/w 直接拒绝/改走切片。
3. **超长截图（h/w > 5）不应靠放大上限解决**：应改用 gundam 切片或分块。当前线索指向
   "A6 的 auto 规则在 h/w>3 时走 base，把 600×3600 压进 1024² 后正文不可读"——本证据的
   特征（**标题可读、正文全是编造**）与该假设一致。A6 是否调整由 Lead 定，此处只提供证据。

再用同一张 D6 复测：

|---|---|---|---|---|---|---|
| D6 base（旧 auto） | — | **runaway** | 12285+（36 min 未停） | — | — | >2160 s，人工终止 |
| D6 gundam（新 auto） | **2713** | **stop** | 2849 | 32.8 s | 561.9 s | 594.9 s |

- 新 auto 下 D6 **正常收敛**（`finish=stop`），输出是连贯正文（开头即
  「# 产品使用手册（节选） … 页眉页脚与页码属于版面噪声，但在部分版式中它们承载了章节信息」），
  与源文内容对得上；
- **2713 tokens 是全部实测文档中的最大值**（D1–D5 最大 2333），仍低于默认 4096

> 不是 token 预算。** 两者要分开调，别用放大上限去掩盖质量问题。

## 7. 建议值：公式值 vs 建议默认值

```
公式值 = clamp( ceil( ceil(p95 × 1.3) / 1024 ) × 1024 , 1024, 8192 )
       = clamp( ceil( ceil(2311.6 × 1.3) / 1024 ) × 1024 , 1024, 8192 )
       = 3072
```

（p95 仅用 D1–D5；D6 是异常类，单列见 §6.2。）

**建议默认值仍取 4096（保持现状）**，理由不是"公式错了"，而是默认值的性质：

1. **上限是天花板，不是目标值**：4096 与 3072 对未触顶的页面毫无差别——正常页在自然
   EOS 处就停（D1–D5 实测 1020–2333）。降低上限只影响"本来会输出 > 3072"的页面，等于
   **只对少数密集页增加截断风险，并不省正常页时间**。
2. **3072 只比实测 max 高 32%，4096 高 75%**：真实扫描件的单元格文字通常比本合成语料长
   （D2 的单元格只有 5–9 字），留足余量比省几分钟更重要。
3. **D6 证明放大与收紧都无益**：runaway 在 4096 之前就已重复；真正的解法在识别/切片侧
   （§6.2 结论 3），不是调这个数。
4. 4096 的最坏单页按实测 4.1–5.2 tok/s 约 **13–17 分钟**（8192 约 26–33 分钟）；3072 只省
   约 4 分钟，且只在触顶页上才体现。

**分档结论（回答"要不要按文档类型分档"）**：

- 实测确实有 2× 跨度：表格 2333 = 正文 1184 的 **1.97×**；双栏 2226 = **1.88×**；
  公式 1486 = 1.25×；代码 1020 = 0.86×。
- 但**单一 4096 已覆盖全部实测最大值（2333）**，且按上面第 1 条，分档对未触顶页面不省
  时间 → **当前不值得分档**（只增加 UI/契约复杂度）。
- 若将来要分档，唯一有意义的方向是给"正文/代码类"降档（例如 2048）以便异常时更早刹车；
  收益是异常时少等 ~4 分钟。**建议等 A6/长截图问题定论后再评估。**

## 10. 局限与风险

- p95 只用 5 份正常文档（n=5），统计意义有限；结论按"类型 + 异常单列"给出，不宣称普适。
- 合成语料的单元格/句子比真实扫描件短，D2 的 2333 可能低估真实密集表格 → 这是保留 4096
  余量的主要理由之一。
- D6 是**异常类**：其 token 数不可作为"需求上限"（在 8192 之前就开始重复）。
- CPU 时长随机器/负载波动（本次 decode 4.1–5.2 tok/s）；上限选择按最坏情形留余量。
- `crop_mode="auto"` 影响视觉 token 与 prefill 时间；本批固定 auto，结论不直接适用于强制
  gundam 的用户。
- 输出 token 含版面标记，模型版本升级可能改变标记密度 → 校准结论有"版本有效期"。
